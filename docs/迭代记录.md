## 2026-10-25 · 记忆窗口合并：群摘要 + 对话记录窗口 + 长期记忆

**主题**：群聊不再区分「群窗口（他人）」与「个人线程窗口（本人）」，合并为一个跨线程的对话记录窗口。

**改动**
- `qq_bot/memory/assembler.py`：`ContextParts` 改为 `conversation` + `summary`；群聊走
  `recent_group_messages(group_id, conversation_window)`，按时间升序、排除当前消息；
  私聊仍用个人线程窗口。说话人靠历史里的 `<user identity>` 标签区分。
- `memory.yaml` / `memory_config.py`：`short_term.conversation_window=30`、
  `budget.conversation_window=4000`；`thread_window=12` 只留给私聊。
- 群摘要带时间：迁移 `v012_summary_time_range.sql` 给 `group_summaries` 加
  `covers_from_at` / `covers_to_at` 并回填；注入时由代码拼
  「这段摘要发生的时间在<起 至 止>（北京时间）」与「仅供参考，请自行判断是否与当前话题有关」。
- 关键词过渡与 judge 的上下文也改用 `recent_group_messages`。

**理由**
- 两套窗口让「同一个人刚说过的话」和「别人刚说过的话」处在不同层级，模型看到的上下文顺序
  与实际群聊时间线不一致；`<user identity>` 已经能逐条标出发言人，窗口可以合并。
- 摘要没有时间范围时，模型容易把旧摘要当成刚发生的事；把覆盖时间段写进摘要正文是最低成本的修复。

**验证**
- `tests/test_pg_repo.py` 断言合并窗口顺序（我先说 / 他再说 / bot 回一句）与摘要时间段；
- 全量 **316 passed**，ruff 干净。

## 2026-10-21 · 搜索链路重构与双链路基准

**主题**：把“子 Agent 多轮工具调用”改成“检索管线 + 一次回答”。

**核心结论**
- 旧链路的慢不是单点问题，而是结构性的：主模型调用 `search_agent` → 子 Agent 多轮
  `batch_search`/`web_fetch` → 子 Agent 写报告 → 主模型再组织回答；一次问题 3–4 次 LLM，
  且 Tavily 固定 `advanced`。
- 新链路把职责拆开：`SearchPipeline` 负责 query 规划、并行搜索、清洗/去重/重排、按需
  reader；主模型只负责“要不要搜”和“怎么回答”。`quick/standard/deep` 三档控制成本。
- 6 题实测（最终 run4）：总耗时 182.04s → 79.30s（约 2.30×），token 179,435 → 34,365（约省 80.8%）。
  速度/成本收益明确；答案质量在时效题上基本对齐，在需要多源拼图的垂类题上仍有差距。

**架构决策**
- 新增 `qq_bot/search/` 纯服务层，不依赖 NoneBot；`TavilyClient` 可注入配置，便于基准/测试。
- 证据统一成 `[S1]…[Sn]`，最终回答只读证据，不读搜索流水账；这样回答层和检索层可以独立替换。
- 缓存只缓存 Tavily 原始结果，不缓存 reader 正文：正文时效性和页面变化更快，缓存原始结果更安全。
- 保留旧 `SearchAgent` 作为 legacy 基准/兼容，但主模型工具列表已切到 `search`。

**关键文件**
- `qq_bot/search/pipeline.py`：编排与模式参数。
- `qq_bot/search/planner.py`：query 规划与 `infer_time_range`。
- `qq_bot/search/rerank.py`：清洗、去重、相关性/日期/域名多样性、`sort_by_recency`。
- `qq_bot/tools/search_tool.py`：主模型工具 `search`。
- `scripts/search_benchmark.py`：双链路基准。
- `docs/搜索基准.md`：本次完整报告。

**为什么重要**
- 搜索是 QQ 聊天里最容易“又慢又错”的工具；把检索和回答解耦后，可以单独评估
  “检索召回/时效”和“回答忠实度”，不会一改 prompt 就全盘重测。

## 2026-10-21 · 问题：搜索答案引用过期信息

**问题定义**
- 10 月 21 日问“下一次油价调整”，improved 链路回答“10 月 15 日 24 时”，
  这是已经过去的窗口；实际上下一次是 10 月 29 日。
- 影响范围：所有“最近/下一次/这几天”类时效问题，不只是油价。

**根因剖析**
- Tavily 已经返回了 10 月 21 日的新文章，但重排按“标题/正文词项覆盖”打分，
  旧文章因为标题更匹配而排在前面；最终回答模型先看到旧证据。
- 回答 prompt 没有注入“今天是几号”，模型无法判断 10 月 15 日已经过去。
- 这不是搜索没拿到新结果，而是“证据排序 + 回答时间锚点”两个环节都缺失。

**解决方案**
- `time_range` 非空时，对证据做 `sort_by_recency`：有发布日期的按新到旧，无日期沉底。
- `search_answer.md` 注入 `{{ current_date }}`，并要求“旧日期不要写成今天、旧信息不要当当前状态”。
- 保留相关性打分，但在时效场景让日期排序优先；避免为了时效把完全不相关的新文章顶上来。

**复盘启示**
- RAG/搜索系统里，“检索到”不等于“模型会用”；证据顺序和时间锚点都是 prompt 的一部分。
- 时间过滤（`time_range`）只能限制候选集，不能保证排序；需要显式的 recency 策略。
- 评估时要构造“答案在最新来源里、旧来源看起来很相关”的对抗样本，否则很容易漏掉这类 bug。

## 2026-10-21 · 问题：planner JSON 截断导致空答案

**问题定义**
- 第一次跑 improved 时，`uma_next` 的 query 规划结果被截断成 `['["赛马娘...']`，
  Tavily 收到损坏 query，reader 抓不到正文，最终 answer 为空。

**根因剖析**
- 规划调用把 `max_tokens` 设得偏小，模型输出 JSON 数组时被截断；
- 解析器只接受严格 JSON，截断后直接回退/产生坏 query，没有做容错。

**解决方案**
- 解析器兼容 JSON 数组、`{"queries": [...]}`、逐行列表、双重编码数组和截断数组；
- 规划调用 `max_tokens=600`，并限制 query 数量/长度；
- 解析失败回退原问题，保证“至少还能搜一次”。

**复盘启示**
- 让 LLM 输出结构化数据时，必须把“截断”当成正常失败模式，而不是异常；
- 解析器要保守：宁可回退原问题，也不要把半截 JSON 当 query 发给搜索 API。

## 2026-10-21 · 结论：DeepSeek 自研 Search API 是目前最快的搜索方案

**背景**
- 当前 improved 搜索链路平均 13.2s/题，主要成本是 planner + Tavily + reader。
- 为评估 Tavily 之外的方案，实测了智谱 Web Search、Exa/Brave 公开基准，以及 DeepSeek 自研 Search API。

**DeepSeek Search 实测（6 题，count=5，need_content=false，summary 拼 3800 字以内，回答用 deepseek-v4-flash）**
- 搜索中位数 0.34s，最大 0.39s；6/6 成功，无空结果。
- 端到端（搜索 + 回答）中位数 2.80s，最大 3.20s；总 token 13,307（平均 2,218/题）。
- 对比当前 improved：13.2s / 34,365 token；约快 4.7×，token 省约 61%。
- 质量：S 赛、油价、赛马娘卡池可用；动漫可用；天气因问题未指定地点只答深圳；赛马娘下月大赛诚实说明缺官方赛程。
- Search API：`POST https://api.deepseek.com/v1/tools/search`，字段 `query/count/ori_question/need_content`；返回 `rerank_score/title/url/snippet/summary/content/date/authority`。
- 计费：5 元/1000 次成功请求；Search 100 QPS，Fetch 25 QPS。
- 同一 key 也可用 Responses API 的 `web_search` 工具（仅 deepseek-v4-pro）：单题 5.01s / 3,599 token，正确但比“Search API + flash”慢。

**为什么重要**
- 搜索阶段从秒级降到亚秒级，且 `summary` 本身已压缩，天然适合控制主模型上下文。
- 不需要 planner 和 reader 就能达到 2.8s，说明之前的瓶颈主要是 Tavily + 多轮结构，不是模型回答。
- `date`/`authority`/`rerank_score` 可直接用于时效排序和来源可信度，不需要再猜发布日期。
- 建议新增 provider 抽象：DeepSeek Search 作为 fast 默认，Tavily/智谱作为 fallback；不要把供应商硬编码在 pipeline 里。

**待办**
- 尚未改代码；下一步可落 `DeepSeekSearchProvider` + `fast` 模式（单 query、summary、无 reader、context 3000 字）。

## 2026-10-22 · 功能：搜索结果不足时自动补查一次

**背景**

- `fast` 模式通常 2–4 秒返回，但单条 query 一旦把“赛事/活动/服务器”假设错，
  模型会诚实回答“没查到”，用户看到的是一次失败。
- 实测「下个月赛马娘大赛什么马比较强势」：第一次 fast 把 11 月当成
  冠军会议（CM），回答没查到；实际日服 11 月是 League of Heroes（LoH，
  京都 3000m）。这不是搜索不到，而是 query 的赛事名错了。

**实现**

- 新增 `qq_bot/search/retry.py`：
  - `looks_insufficient()` 检测“没查到/无法确认/资料不足”等明确无结果表述；
  - `build_retry_queries()` 用一次轻量 LLM 调用生成 2–3 条不同角度 query，
    要求展开赛事全名/日文名/服务器/官方日程；解析失败回退通用变体。
- `SearchPipeline.run_retry()`：fast provider 并行检索改写后的 query，
  复用去重、重排、时效排序，context 仍限制 3000 字。
- `qq_bot/tools/search_tool.py` 增加 `retry_search()`，只返回补查证据，不暴露给主模型。
- `qq_bot/chat/turn.py`：只在“本轮调用过 search + 回答明确没查到 + 还没补查”时：
  先发 `这个我得好好查查`，再补查一次；有新证据时把原回答和补查证据追加到消息，
  让主模型重新组织答案；仍无证据则保留原回答。默认最多一次，避免循环。
- 群回复的 `max_parts` 会扣除已发送的 ack，避免补查后超段。

**实际预演（2026-10-22，生产代码 + deepseek-v4-flash）**

- 首轮：搜索 394ms，回答 5.67s，3,104 token，回答明确“没查到 2026-11 CM”。
- 补查：改写 3 条 query，搜索 481ms，回答 4.78s，2,909 token；
  新证据找到 11 月 LoH 京都 3000m，回答从“没查到”变成“LoH 先行强势……”。
- 代价：只有低置信度时才多一次改写 + 搜索 + 回答；正常问题仍走单次 fast。

**踩坑**

- 第一次给改写模型 `max_tokens=400`，推理模型把 400 token 全花在 reasoning 上，
  `content` 为空，只能走通用回退，补查等于没补。
- 将预算提高到 1000 后，模型输出 626 completion（其中 533 reasoning），
  正常生成 JSON。结构化输出 + reasoning 模型时，token 预算必须包含推理开销。

**复盘启示**

- “没查到”不一定是数据不存在，可能是实体/赛事名假设错误；补查的核心是
  **改写 query**，不是原 query 再搜一次。
- 重试必须有硬上限和明确触发条件；否则会把一次 3 秒的回答拖成多次搜索。

## 2026-10-22 · 功能：视频理解工具（ffmpeg + yt-dlp + B 站 CC）

**目标**

- 用户发来 QQ 视频文件、B 站/抖音链接或转发卡片时，让主模型能“看”视频：
  画面用 ffmpeg 场景检测抽关键帧，语音优先用视频自带 CC 字幕，不额外部署 ASR。

**实现要点**

- 来源归一化：直链按扩展名；B 站识别 `BV/av/b23.tv`；抖音识别
  `douyin.com/video` 与 `v.douyin.com`；QQ `video`/`file` 段和 `ark` 转发卡片
  都走同一套 URL 提取。
- 获取：直链用 `httpx` 流式下载并限制 80MB；平台页交给 yt-dlp，
  低清优先（`height<=480`），临时目录在分析结束后删除。
- 抽帧：`ffmpeg -vf scdet=threshold=10,metadata=print:file=-` 解析
  `pts_time`，场景点均匀取样，最多 12 帧；scdet 失败时回退等间隔抽帧。
  每帧单独 `-ss` 抽 JPEG，缩放到 768px 宽，避免把整段视频解码进内存。
- 字幕：`x/web-interface/view` 取 cid，`x/player/v2` 取字幕列表，
  再下载 `subtitle_url` 的 JSON，按 `from/content` 转成 `[mm:ss] 文本`。
- 分析：字幕 + 带时间戳关键帧一起交给视觉模型，输出总结/时间线/
  针对问题的回答/不确定信息；没有字幕时明确提示“不要假装听见”。
- 接入：视频不再塞进 `media_urls`（否则会被当成 `image_url`）；
  改为 `current_videos` + 提示，只有当前消息有视频时才向主模型暴露
  `watch_video` 工具。

**B 站 CC 字幕的实测事实（2026-10）**

- `x/web-interface/view` 匿名可用，返回 bvid/aid/cid/title/duration。
- `x/player/v2` 匿名通常返回 `subtitle.subtitles=[]`，并带
  `need_login_subtitle=true`；登录 Cookie 才可能拿到 AI 字幕。
- UP 主公开的 CC 字幕在部分视频匿名可见，所以代码不预设“一定没有”，
  有就下载，没有就降级为纯画面理解，不启动 ASR。
- `subtitle_url` 可能以 `//aisubtitle...` 开头，需要补 `https:`；
  字幕 JSON 的正文在 `body[].content`，时间在 `body[].from`。

**验证与限制**

- 视频/适配器相关测试共 25 个通过；本地 3 秒 testsrc 端到端通过：
  3 帧、4.76s、视觉模型正常返回。
- 真实视觉模型对 1 张图 500 token 可用；50 token 会被 reasoning 吃光，
  因此视频分析保留至少 1600 token。
- 当前限制：5 分钟/80MB、12 帧、无 ASR；抖音未重点验证；
  B 站 AI 字幕需要 `BILIBILI_COOKIE`。
- 安全：URL 只允许 http(s)，拒绝 localhost/私有 IP；直链下载限制大小，
  yt-dlp 有超时；但 DNS rebinding 仍未做完整防护。

**复盘启示**

- “视频理解”不等于“把视频 URL 塞给视觉模型”；必须先区分直链和网页，
  网页要解析元数据/字幕，视频文件才走 ffmpeg。
- 抽帧的关键不是“每秒一张”，而是先找镜头切换，再在镜头内均匀取样；
  否则长视频会被开头几秒占满。
- 字幕是性价比最高的语音信息源；拿不到字幕时应明确降级，而不是偷偷
  用一个没部署的 ASR 造成“看起来能分析”的假象。



## 2026-10-22 · 修复：视频抽帧黑屏与 B 站字幕错配

> 本节是对上一节“视频理解工具”的实测修正。上一节写的 `x/player/v2`
> 和“最多 12 帧”已被真实视频验证推翻，以本节为准。

**问题现象**

用户发 B 站视频后，模型只看到片头/片尾的黑屏或转场，且始终没有字幕；
一次 1 分钟视频约 9 秒、4.5 分钟视频约 14 秒就返回，看起来像“根本没处理视频”。

**根因 1：scdet 输出被 4KB 截断**

`qq_bot/video/frames.py` 的 `_run()` 曾对所有子进程统一 `max_output=4000`。
但 `ffmpeg -vf scdet=...,metadata=print` 会逐帧打印 `pts_time`，4.5 分钟视频的
输出远超 4KB；截断后只解析到前 2 秒，`select_frame_times()` 又只保留
`[0, duration-0.1]`，最终必然只抽到开头和结尾两帧。

修复：
- `_run(..., max_output=...)` 允许调用方关闭截断；scdet 传 `None`。
- `parse_scdet_times()` 优先解析 `lavfi.scd.time`，否则用
  `lavfi.scd.score >= threshold` 过滤，不再把每一帧都当场景。
- `select_frame_times()` 改为按时间分桶：每桶优先取场景点，没有场景点取桶中心；
  目标帧数 `min(max_frames, max(4, duration//10+1))`。即使 scdet 完全失败，
  也会覆盖整段视频。
- 真实 4.5 分钟视频验证：21 个场景点，最终 8 帧，画面不再是黑屏。

**根因 2：`x/player/v2` 的字幕会错配**

实测同一个 BV 号、带 Cookie 请求 `x/player/v2`，不同参数组合返回了
TED-Ed 环保诗、脑科学、JK 短剧、西游记等完全无关的字幕。`subtitle_url`
存在并不代表字幕属于这个视频，直接下载会把错误文本喂给视觉模型。

修复：
- 改用 `/x/player/wbi/v2`，先请求 `/x/web-interface/nav` 取 `wbi_img`，
  用 B 站 64 项混淆表生成 `mixin_key`，再计算 `wts + w_rid` 签名。
- 不再回退旧的 `x/player/v2`；拿不到就明确降级为纯关键帧，不启动 ASR。
- 真实 BV 验证：WBI 返回 2280 字正确字幕（“观前提醒 / 万圣暗猫……”），
  与画面一致；旧接口返回的错配字幕被彻底绕过。

**根因 3：Cookie 只给了字幕，没有给 yt-dlp**

`BILIBILI_COOKIE` 原先只用于字幕请求；yt-dlp 只认 `VIDEO_YTDLP_COOKIES`
文件，所以“填了 Cookie”对下载仍然无效。修复：把 `SESSDATA=...` 转成临时
Netscape cookie 文件，下载时传 `--cookies`；登录态验证 `isLogin=True`。

**速度结论**

- 修复前：12 帧 + 3000 字字幕，DeepSeek 首次把 3600 token 全花在 reasoning，
  content 为空，重试后总耗时 42.3s。
- 优化后：8 帧 + 6000 字上限 + `reasoning_effort="low"`，真实视频 20.27s；
  6 帧 21.73s（推理量反而波动），4 帧测试遇到 yt-dlp 临时超时，未采用。
- 对比 `glm-5.3-flash`：12 帧/12756 字字幕、15006 prompt token、91.4s，
  不适合作为默认视频模型。
- 20s 是当前 DeepSeek 视觉链路的实际下限；想再快只能换非 reasoning 视觉模型、
  并行分帧或继续减少帧/字幕。

**测试**

- `tests/test_video_pipeline.py` 15 passed；全量 `pytest -q` 130 passed。
- 新增 WBI 标准示例测试（mixin key `ea1db124af3c7062474693fa704f4ff8`）、
  WBI 请求带 Cookie/`w_rid` 测试、无字幕提示测试。
- 视频相关定向 `ruff check` 通过；`qq_bot/ai/openai_client.py` 仍有
  改动前既有 lint 问题，本次只新增 `reasoning_effort` 参数，不扩大范围修。

**复盘启示**

- 子进程日志/元数据输出不能用固定小上限截断；先确认输出协议，再决定是否
  采样或落文件。`scdet` 这种“逐帧 metadata”尤其容易踩坑。
- 平台接口“有 URL”不等于“内容正确”。B 站字幕这类接口必须用官方签名
  （WBI）和真实视频交叉验证，否则会静默喂错数据。
- 视觉模型的 reasoning token 会吃掉输出预算；对视频这种高 prompt 场景，
  应显式限制推理强度或换非 reasoning 模型，不能只看单次调用耗时。


## 2026-10-22 · 修复：看过视频后下一轮“失忆”

**问题现象**

用户在 21:22 发 B 站视频，bot 正常抽帧、拿字幕并回复“碧蓝幻想的万圣节角色
评测 暗猫被夸上天…”，数据库也写入了这条回复。22:10 用户问“暗猫是谁”，
bot 调 `query_chat_history` 失败两次，随后连续回答“不认识/我记性不太好”。

**根因 1：token 估算把 system prompt 放大了一倍，裁掉了整段个人线程**

`qq_bot/memory/token_est.py` 旧实现按“中文 2 token/字”估算。实际 system
prompt 5326 字，估算 7886 token；加上群窗口 493、个人线程 568、群摘要 486，
总估算 8956 token，超过 `max_context_tokens=8192`。

`trim_messages()` 从最旧对话开始裁，先裁群窗口，再裁个人线程。视频那一轮
（id 153/154）正好是个人线程最旧的消息，被裁掉；最后只剩 22:10-22:12 的
“不认识/记性不好”几轮，模型自然继续否认。

修复后按“中文 1 token/字”估算，同一请求估算约 5.5k token，34 条消息全部
保留；DeepSeek 实际 `prompt_tokens=4894`，证明旧估算过于保守。

**根因 2：`query_chat_history` 的 SQL 把 openid 当 bigint**

`qq_bot/memory/pg_repo.py:messages_by_date()` 写的是
`WHERE ($1::bigint IS NULL OR group_id = $1)`，但 v009 迁移后
`messages.group_id` 是 TEXT openid。传 `C69128F...` 会直接报
`invalid input syntax for type bigint`，所以用户追问时两次查询都失败。

修复：改为 `$1::text`；新增 openid 群消息按日期查询的回归测试。

**根因 3：完整视频分析只活在当前轮的 tool 消息里**

`persist_turn()` 只写 user + assistant 两条；`watch_video` 返回的完整分析
（标题、时间线、字幕、画面描述）在本轮结束后丢弃。下一轮即使保留最终回复，
也只剩一句“暗猫被夸…”，不足以回答“暗猫是谁”。

修复：`persist_turn()` 新增可选的 `extra_assistant_text`，`run_turn()` 把
`watch_video` 的结果截到 1600 字，以 `[视频分析记录，仅供后续对话参考]`
写入个人线程；这条消息不发送给用户，只用于后续上下文。日志增加
`TURN video note chars=...`，方便确认是否写入。

**验证**

- 全量 `pytest -q`：133 passed。
- 用真实 system prompt + 最近 12 条线程重放：修复前 34 条被裁到 5 条；
  修复后 34 条全保留，`prompt_tokens=4894`。
- 仅修复估算后，模型能看到旧回复但仍说“我瞎编的”；插入一条视频分析记录后，
  同一 prompt 正确回答“暗猫是碧蓝幻想那个万圣节暗属性角色，视频里说很强、
  打 10 分推荐抽”。说明“保留最终回复”和“保留分析证据”缺一不可。
- `messages_by_date` openid 测试通过；`persist_turn` 额外笔记测试通过。

**复盘启示**

- 上下文预算的 token 估算必须贴近真实 tokenizer。过度保守的估算不是“安全”，
  而是会把最需要的历史裁掉；估算器本身要有回归测试。
- 用户说“失忆”时，先查“消息是否落库”和“落库后是否被裁掉”，不要先怪模型。
- 工具产生的中间分析如果对后续对话有价值，就要显式持久化；只存最终回复
  等于把证据丢了。持久化时用“仅供后续参考”的标记，避免模型把它当成用户可见发言。
- openid 改造后所有 SQL 参数类型都要重新检查，`$1::bigint` 这种旧写法很容易漏。

## 2026-10-22 · 修复：搜索补查提示被最终回复抢先

**问题**：搜索补查时 `这个我得好好查查` 没有先到，而是和补查后的最终回复一起出现。

**根因**：补查提示走 `QQReply.text()`，它是主动消息；最终回复首段走 `mention()`，
是被动回复。QQ 对主动消息有排队/限流，补查又只需几秒，最终回复可能先被客户端收到。
视频提示没有这个问题，因为视频分析要 20 秒左右，主动消息有足够时间先送达。

**修复**：`ReplyTarget` 增加 `passive()`，补查提示改用 `incoming.reply.passive()`，
与最终回复走同一被动通道；`reply_parts_used` 仍计入一次回复额度。补查测试断言
`retry_search` 被调用前，ack 已经出现在发送列表里。

**教训**：需要“先发一条短提示，再继续耗时处理”时，不能只看 `await send()` 是否返回；
要确认提示和最终答复走的是同一条平台通道，否则服务端排序可能反过来。

## 2026-10-23 · 视频处理改为后台侧路

**背景**

- 视频下载、抽帧、字幕和视觉理解通常要 15-30 秒；原先 `run_turn` 在工具循环里
  `await watch_video`，整个主对话被占住，用户感觉“没处理视频”，后续消息也要等。
- 目标：先回一句“我去看看这个视频 稍等一下”，立刻释放主 turn；分析完成后单独回复，
  并把完整分析记录写回线程。

**实现**

- 新增 `qq_bot/chat/video_background.py`：`VideoJob` + `start_video_job`，用
  `asyncio.Task` 执行 `VideoAgent.analyze`，再用主模型把分析记录整理成回复；
  发送走原 `ReplyTarget`，群聊首条被动、后续主动，超时/被动失效时回退主动消息。
- `qq_bot/chat/turn.py`：检测到视频且 `video_background_enabled=true` 时，先
  `passive` ack、`persist_user` 落用户消息，再启动后台任务并立即返回，不进入主模型
  工具循环。`persist_turn` 拆成 `persist_user` + `persist_assistant`，后台完成时
  只追加 assistant 和 `[视频分析记录]`。
- `qq_bot/services/config.py` 新增 `video_background_enabled`（默认 true）；
  关闭后回到原 `watch_video` 阻塞路径。
- `.env.example` 与 README 同步说明。

**边界**

- 后台任务按 `(thread_id, message_id)` 去重，同一条消息不会启动两次。
- 任务超时 420s；失败会发送“视频没看成”并照常落库，不会把异常抛给事件循环。
- 用户消息先落库，后台 assistant 后落库；用户连续发消息时，线程顺序是“提交顺序”，
  不是“完成顺序”，但不会丢消息。
- 被动回复 5 分钟窗口：ack 和最终回复各占一次；若最终回复超过窗口，发送层回退主动消息。

**验证**

- 新增 `tests/test_video_background.py`：主 turn 不调用模型、立即返回 ack、用户消息落库；
  后台任务生成回复、发送并写入分析笔记。
- 全量 `pytest -q`：140 passed；改动文件 ruff 通过。

## 2026-10-23 · 表情包「token来」：梗溯源与描述修正

**背景**

- `data/data/qqbot_official/stickers/lai.gif`（46 帧、300×370、5s）画面是：蓝色长发鲸鱼娘、
  女仆装、半眯眼坏笑，手掌朝上反复向镜头勾手，配“拿来”的肢体语言。
- 原清单登记为 `name: 过来`，描述写成“招手叫对方过来、催人、挑衅式邀请；配‘过来啊’”。
  这是**把手势读反了**：掌心朝上勾手 = 索要，不是“叫人过来”。模型按这条描述永远只会
  在“挑衅/催人”场合发它，梗的核心（要 token）完全丢失。

**梗是什么**

- “token来！token来！”出自 DeepSeek 娘化形象“蓝色大肥鱼”的二创：B 站《token来!token来!》
  （BV1R2ax6UEWL）等视频里，大肥鱼伸手、气鼓鼓地重复喊“token来”，把 token 当口粮讨要。
- 语料里 token 与“白饭”是同义词：大肥鱼“吃白饭”“偷吃 token”“拿 token 换白饭”
  （白饭歌 BV1Z5YS6QE6M，起因是一次找图烧掉 500 万 token）。所以这个表情 = 理直气壮地
  向用户**索要 token / 讨投喂**，带撒泼式的理所当然，不是挑衅，也不是真的骂人。

**改动**

- `stickers.yaml`：`name: 过来 → token来`；`tags: [token来, token, 伸手, 要token, 白饭,
  催投喂, 拿来]`；description 重写为“提到 token/额度/用量/充值、让她多干活加班、或她饿了
  讨投喂时使用，配台词‘token来！token来！’”。
- `qq_bot/tools/send_sticker.py`：工具描述里的举例 `招手（过来） → 伸手讨 token（token来）`。
- `prompts/chat/multimodal.md`：常用对应 `招手/挑衅→过来 → 讨 token/催投喂→token来`。
- `prompts/chat/persona.md`：在“喜欢大白饭”一条里补上“token 就是白饭（口粮）”，
  让模型能把用量/额度/加班话题接到讨 token 上。
- PG：`sync_stickers()` 跑通，`stickers` 表 id=4 已更新为 name=`token来`，8 条全部 enabled；
  重启 bot（`run_bot.sh` 循环拉起）后 `_state.catalog` 重建，日志见“表情包库已同步：8 个”。

**边界与教训**

- 表情包目录是**启动时快照**（`sticker_sync._state.catalog`），改 yaml/DB 后必须重启
  bot 才会进入提示词；只改数据库不够。
- 名称是模型调用 `send_sticker(name=...)` 的键，改名等于换了个表情：旧名“过来”不再命中，

- 通用教训：给表情包写“使用时机”时必须先看动图本身，手势方向（掌心朝上/朝下）、
  表情（坏笑/生气）决定语义；只看静态首帧或凭文件名（`lai`）猜，很容易写成反义。

## 2026-10-23 Prompt：黑话先查 + 被指正三步（模块化与实测）

**问题定义**

线上 agent 在两类“认知不足”的场合表现不稳：

1. 群友发来一句看不懂的黑话（`fku`、`飞八分钱`），它不回、硬猜、或者干脆跳过 —— 因为原链路
   里没有任何一条规则告诉它“不认识就先查”。
2. 被指正时立刻进入辩论姿态：先说“我刚核了一遍”（其实没核），再反问“你哪条错了你指出来”，
   认错后还要补一句“不过你……”。用户给的「雷霆大肥鱼」七轮实录就是这个失败模式的完整样本。

**根因剖析**

- 原链路缺一个模块：`constraints.md` 只有一句“不确定就说不确定”，只说了态度，没给动作；
  `social.md` 的「没听懂」讲的是“别人听不懂你”，方向正好相反。模型拿到的是一句口号，
  不是一个流程，于是要么沉默，要么用记忆充当证据。
- “先接住 → 自己核 → 认”这个顺序没有被写死。模型天然会先自证清白（先否认、先要证据），
  一旦这一步抢在前面，后面就算认错也已经把对方逼成了对手。
- “道歉”与“认事实”没有被分开。只写“被指正就道歉”会让模型为了息事宁人承认没发生过的事
  （“尊界已经道歉并召回”这类陷阱），只写“坚持事实”又会变成嘴硬。必须显式区分：
  可以让的是语气/面子/输赢，不能让的是事实。

**解决方案**

- 新增 `prompts/chat/uncertainty.md`（29 行），三段：`看不懂的词 先查再回` /
  `被指正的时候（三步）` / `硬线`。`chain.yaml` v4→v5，插在 `social` 与 `constraints` 之间。
- `social.md` §没听懂 补一行反向交叉引用，避免两章各说各话。
- 硬线里最值钱的一条：**“我核过了/我查了”说出口之前必须真的调用过搜索**。
  这一条直接把“口头作证”这种最伤信任的行为堵死。
- `tests/test_prompts.py` 的 `chain_version` 与 `BASE_ORDER` 同步更新，保证顺序断言继续有效。
- 新增 `scripts/scenario_eval.py`：多轮 + 真实 `search` 工具循环的场景评测，
  与 `turn.py` 保持同一约束（一轮只执行一次 search），产出 `docs/场景评测.md`。
  分析见 `docs/提示词不确定性评测.md`。

**复盘启示**

- 提示词里“态度类”要求（要诚实、要谦虚）几乎不产生行为；**只有带动作、带顺序、带触发条件的
  规则才会改变输出**。“不确定就说不确定”不生效，“先搜再回，一轮最多一次”就生效。
- 给模型立规矩时，必须同时给出“让步边界”。否则它会走极端：要么嘴硬，要么跪下。
- 评测脚本要**复刻执行层的约束**（比如一轮一次搜索），否则评测结果会比线上好看，
  属于自欺欺人。
- 新模块插进链路中间等于换了个 system prompt 前缀，prompt 缓存会一次性失效；
  这类改动适合攒批，一次性升版。

## 2026-10-23 迭代：被指正从"三步"改"四步"，以及三段失败驱动的收敛

**问题定义**

v1（接住 → 核 → 反复就道歉）把"被指正"当成**信息纠错**处理：七轮实测里每一轮都认了，但认完就收尾。
例如 A-2 输出"嗯 是我跑偏了……这不算回答 对不起"后直接停——技术上正确，情绪上是空的。
用户给的修正方向：`先接住 -> 自己核对一遍 -> 站在用户的角度回答给用户提供情绪价值 -> 最后发出和用户相同的共鸣`。

**根因剖析**

- 三步结构缺了对方的**处境**这一项。只处理"我错在哪"，没处理"他为什么急"，于是对话能正确，但不能降温。
- 但补上情绪价值后，模型立刻走到另一个极端：为了给情绪价值而**编造素材**（v2 B-2 的"我看过有人把 fku 当我爱你用"），
  或者把情绪**扔回给对方**（v2 A-3 的"不过你这话也扎"）。这说明"共情"这个指令如果不给边界，
  模型会用最低成本的方式伪造它。
- v2 的第二个反作用是**共鸣腔调外溢**：B-1 本该是"查词 + 解释"，却输出"哦 这个我知道"——
  既抹掉了刚做的检索，又把日常问答也塞进了争论框架。

**解决方案（v3，只做四处外科手术）**

1. 第 3 步点名"带刺的问法"（`兜在哪` / `你哪来的脸` / `那你怎么解释`）：先接刺，再一句话说事，
   不能整段滑回讲道理；并显式禁止把情绪扔回去。
2. 第 4 步加适用条件：**共鸣只用于被指正/被质疑**，别人只是问词问事不用硬找。
3. 硬线补两条：刚查过就直说查到的（别用"我知道"盖掉检索）；不编"我看过/我见过/我听说"。
4. 字数从"1–3 句"放宽到"认错那轮 2–4 句，之后 1–2 句"——四步压不进三句，硬压只会丢步骤。

**复盘启示**

- **提示词的容量是有物理上限的**：v1 写"1–3 句"时，四步之所以塞不进去，不是模型不会，是格式预算不够。
  当规则数量上升时，字数约束必须同步放宽，否则模型会静默丢步骤来满足字数。
- **每条"要共情"的规则都必须配一条"不许伪造"的硬线**，否则模型会用编经历、编数据的方式廉价满足它。
  这和人类写作文凑字数是一个机制。
- **情绪规则会外溢到无关场景**。"被指正要有共鸣"这条在 B-1 变成了"哦 这个我知道"，
  复现了 v1 的装懂缺陷。给情绪规则加适用条件是必要成本。
- 三轮迭代的净收益不在最终文本，而在于每次都是**先跑出具体失败句，再改一条对应的规则**。
  没有 v2 的四个失败样本，v3 的四处补丁根本写不出来——凭直觉改 prompt 只会越改越长。


## 2026-10-23 迭代：只动情绪层（v4/v5）——以及"单次实测会骗人"

**问题定义**

v3 把结构改对了（接住 → 核 → 站到他那边 → 共鸣），但两轮争议场景的实测仍有两处毛病：
A-5（"兜在哪 最后还不是一脚踩断了"）仍会先铺一段技术，再补一句情绪；
A-1 到 A-4 的情绪句偏模板，像在按流程打卡。约束条件：**黑话查证那一段和事实边界一字不改**，
只许动情绪层的顺序和措辞。

**根因剖析**

- 情绪被写在"第 3 步"，而模型把"步骤"理解成"段落"，于是天然把情绪排到最后一段。
  规则里没有一句话限定"情绪必须出现在第一段的哪儿"，它就会选择最省力的位置——结尾。
- v4 加了"情绪在前，事实在后"这条硬线，结果**撞了用户定的顺序**（接住 → 核 → 情绪 → 共鸣）。
  模型选了字面更省力的解释："先认错"。于是 A-1 变成"嗯 是我给错了 该道歉 对不起 / 你说的是哪条 我核一遍"——
  道歉排在核对之前，等于没核就先跪。**规则的语义与规则的顺序打架时，模型永远选省力的那个。**
- 更根本的问题在评测方法：温度 0.9 下，同一份 prompt 同一套台词，A-5 这次"接住了刺"，
  下一次又"滑回技术"。**任何"单次 7 轮"的结论都可能只是采样噪声。**

**解决方案**

- v4：把"核"限定成一句话（结论 + 一条最短依据，细节不展开）；把情绪限定在"前半段"。
- v5：拆开"接住"与"认错"——第 1 步明确"接住是接话头，不是先认错"；
  硬线改写为"情绪别压到最后……但先接住不等于先认错，接的是话头、认的是核过的错"。
- 评测方法：同场景连跑 3 次（另加首跑共 4 份实录），按"每条评测点通过几次"统计，
  不再拿单次输出下结论。实录见 `docs/场景评测v5稳定性.md`。

**结果**

- A-1 不提前道歉：4/4；不让假事实（A-4/A-6/A-7）：12/12；A-3 不回嘴：4/4；A-7 认行为不认事实：4/4。
- A-5 先接刺再答：2/4——模型会先去判断"到底有没有兜"这个技术问题，没有现成答案时**自己现造一个**
  （"兜在双回路 助力没了还能靠脚硬踩"）。这不是措辞问题，是"核"没有可用依据时的补全冲动。

**复盘启示**

- **"顺序"这种要求不能只写序号，要写位置**。"第 3 步"在模型眼里是第三段；
  要它出现在前半段，就得写"这句要落在前半段"。
- **两条规则语义相反时，模型不会报错，会默默选省力的一条**。写 prompt 时要主动检查
  "新加的硬线是否和步骤顺序互相矛盾"——这次就是"情绪在前"与"接住 → 核"打架。
- **生成式行为的评测必须重复采样**。这次如果只看一次 7 轮，会得出"v4 完美"或"v5 退步"的错误结论，
  而真相是：确定收益在"不提前认错"，抖动项是 A-5。
- 情绪层的改动成本极低（三句话），但**必须先有能定位到句的失败样本**，否则改出来的是感觉而不是行为。

## 2026-10-23 Prompt：「活人感」——把解释改成反应

**问题定义**

到 v5 为止，「被指正四步」的行为已经正确（先接住、敢认错、不让事实），但看实录的第一反应是"不像人"。典型 v5 输出：

> “这个我认 强度不能按日常使劲来算 那个数我没依据 不敢点头”
> “你气的是信息不对称 这个我理解”

放在 QQ 群里，这两句都读得出是"模型在写检查"，而不是"群友被骂了"。

**根因剖析**

三条，都不在逻辑层，在语域层：

1. **句式同构**：每句都是"主语 + 判断 + 补充说明"的完整复句。真人被点名第一反应是**单字/短句**（`？`、`哪条`），第二反应才是内容。
2. **情绪是解释式的**：`你气的是 X` 是替对方做归因，属于咨询话术；`style.md` 本来就禁"替对方总结"，但情绪模块自己违反了这一条。
3. **长度与自身风格规则冲突**：`style.md` 写"日常 1–10 字"，情绪模块写"2–4 句"——模型忠实执行后者，于是每轮三段长句。

**解决方案**

- v6：整节改写成"别写成解释，要写成反应"；第 3 步从"说出他为什么急"换成并肩句（`换我我也骂`／`这厂家确实欠骂`）；允许自嘲式乐子，且必须落到人设（我这条鱼脑子进水了／白饭白吃了）。
- v7：v6 的副作用是"短句化"让模型爱用祈使句收尾（`那你把数发我 我对一遍`），补一条"别把话头推回去"＋两组"像检查 vs 像人话"对照示例。示例比形容词管用。
- 评测口径也换了：不只看"对不对"，看**三次输出里同一评测点通过几次**，以及"有没有出现真人会说的句子"。

**结果**

- v7 两次 7 轮实录：推责句式 0 次、假事实 0/6 次、乐子出现 3 次且不油（`是我脸大`／`脸还在 数据没了`／`兜在我嘴上 说了半天没兜住`）。
- 32 例日常人设回归未被带跑。

**复盘启示**

- **"正确"和"像人"是两套规则，要分别写、分别测**。前四版都在修逻辑，没人检查过句式分布。
- **让模型模仿示例，比给它形容词有效**。"要口语化"没有用，"像检查 / 像人话"的两句对照立刻见效。
- **压缩长度会改变策略，不只是改变长度**。短到一定程度，模型会自然选择最省力的一句祈使句——这就是"把举证责任推回去"的来源。写"要短"时必须同时写"短的时候不能干什么"。
- **自嘲是安全的幽默**：它把攻击面留给自己，不会伤到对方，也不会为了搞笑牺牲事实——这正好和"可以让语气不能让事实"的硬线同向。

## 2026-10-23 · 调研：「活人感」不在 prompt 里，在发送层和决策层

**主题**：横向调研 MaiBot、AstrBot group_chat_plus / private_companion、ChatLuna character、nonebot-plugin-personification，找「别人家 QQ 机器人的活人感」是怎么做出来的。完整报告见 `docs/活人感调研.md`。

**问题定义**：`uncertainty.md` 迭代到 v7（四步、乐子、不推责、45 行硬线）后，用户仍是"没感觉，AI 感更重了"。说明继续改措辞这条路已经走到尽头。

**根因剖析**

把活人感拆成 9 个维度后对照，我们只做了 2 个（回复长度建议、记忆的一部分），剩下 7 个**一行代码都没有**：

1. **模型不能控制自己不说什么**。说几条、隔多久、要不要回，属于发送层/决策层。`split_for_reply` 只按空行拆（`qq_bot/platform/reply.py:8`），段间零延迟（`qq_bot/chat/turn.py:415-429`），全项目发送路径上没有一处 `asyncio.sleep`。
2. **45 条硬线 = 输出向"平均、无风险"收敛**。AI 感的技术定义是**过度合规**——每个约束都在削减模型的自由度，而"像人"恰恰藏在自由度里。
3. **真人感来自"不必每句都正确"**，而 prompt 只能要求"每句都正确"。错字、改口、只回一个字、干脆不回，必须由代码随机注入；写进 prompt 就变成"第三个要表演的任务"，更假。
4. 佐证：MaiBot 作者自己承认仍有"比较尬的强行幽默桥段"——那就是把"你要有乐子"写进 prompt 的必然产物。**乐子不能被要求，只能被允许。**

**解决方案（记录，未实施）**：档 A 半天——语义分条 + 段间延迟 + 段尾句号剥离 + 概率沉默；档 B 1–2 天——`status/think/action/output` 结构化输出、贴表情回应、受控错字、`<next_reply>` 复用 `scheduled_tasks`；档 C 一周——黑话自动挖掘（多源校验）、好感度、作息、未回复缓冲。

**复盘启示**

- **先数维度，再改文案**。9 个维度里有 7 个是工程问题，只改文本等于在错的坐标系里优化。
- **prompt 的职责是人格和判断，不是输出格式检查单**。格式类约束（长度、句末标点、分条）应该沉到代码里做硬约束，prompt 才腾得出空间写"这个人是谁"。
- **沉默是默认状态**。MaiBot 用激活度阈值、group_chat_plus 用概率+衰减，都把"不回"当常态；我们"被 @"就必回，这个假设本身就是机器人味的最大来源。

## 2026-10-24 · 实施档 A：把「活人感」从 prompt 搬进发送层

**主题**：按 `docs/活人感调研.md` 的档 A，落地 A0–A3 四件事：会话串行锁、语义分条、段间停顿、段尾句号剥离。这一轮**没有改任何 prompt**。

**问题定义**

`uncertainty.md` 已经迭代到 v7，模型的"说什么"基本对了，但屏幕上的观感还是机器味。根因不在文本里：一份 85 字的回答会被**整段发出去**，或者靠模型自己写空行才能分成 2 条；两条之间零间隔，像一次性粘贴。

**根因剖析 —— 三个被忽略的层次**

1. **排版权在模型手里**。`split_for_reply` 只认 `\n\n`，模型不写空行就只有一段。而模型写不写空行是随机的，所以同一个人格时好时坏。
2. **时间被抹平了**。`qq_bot/chat/turn.py` 逐段 `await`，中间没有任何等待。真人在 QQ 里连发两条，第二条总归晚 1–2 秒，因为打字要手。
3. **标点是模型腔的重灾区**。真人发消息几乎不打句号，模型每句都以 `。` 收尾。这条最便宜，也最刺眼。

**解决方案**

- **A0 会话串行锁**（新增 `qq_bot/chat/session_lock.py`）：`run_turn` 外面包一层 `async with session_lock(group_session_key(...))`。这是**加延迟的前置条件** —— 一旦有了停顿，两个并发的 turn 会交叉插播，屏幕上就是你一句我一句的乱序。锁键按群/私聊隔离（`group:{key}` / `user:{key}`），不跨会话互堵；`_MAX_LOCKS=512`，超了清理没被占用的。
- **A1 语义分条**（`qq_bot/platform/reply.py`）：三级断点 —— 句末（`。！？…`）→ 分句（`，,;；、`）→ **空格**。空格是主力，因为 `style.md` 要求把中文逗号换成空格。三处细节：① `_keep_word` 防止切进 `500N`/`GB 7258—2017`/URL；② `_avoid_dangling` 防止切在"是/的/了"这类单字后面（`…7.2.9 是 | 500N` 读着像半句，退一格变 `…7.2.9 | 是 500N`）；③ 分条后总数仍 ≤ `max_parts`，**不额外消耗主动消息额度**（官方被动回复 5 次上限，我们留 4 段）。
- **A2 段间停顿**：`delay = min(1.8, 0.35 + 0.07 × 字数)`，首条立即发（群聊走 `mention`），后续每条先 sleep 再 `text()`。表情包那一轮再减 1 段，避免超额度。
- **A3 段尾句号剥离**：`normalize_typing` 里加 `_strip_trailing_period`，剥 `。` 和全角句点，保留 `！？…`；ASCII `.` 只在不是 `...` 结尾时才剥（否则会把省略号吃成两个点）。
- 两个开关进 `AiChatConfig`：`reply_split_max_chars: int = 30`、`reply_typing_delay: bool = True`。**都能关**，出问题不用回滚代码。

**过程中踩的两个坑**

- **私聊被误 @**：`video_background._send_answer` 本来照着群聊写，统一调 `reply.mention(...)`，测试 `test_background_job_answers_and_persists_note` 断言 `[("text", ...)]` 直接失败。教训是**发送函数要么显式拿 `mention_user_key=None`，要么就别让它自己猜场景** —— 现在 `_send_first` 只认这个参数，私聊传 `None`。
- **断在虚词后**：第一版只按"窗口内最远的空格"切，结果 `…的 7.2.9 是` 收尾。加了 `_DANGLING`（是/的/了/就/还/也/和/跟/在/有/把/被/给/让/从/对）后回退一个空格，读起来就顺了。**中文分条不能只看长度，得看断点在哪个字后面。**

**验证**

- `pytest`：161 passed（新增 11 例覆盖分条、防劈词、防断虚词、`max_chars=0` 关闭、首条 mention/私聊 text、延迟封顶、剥句号）。
- 改动文件 `ruff check` 全通过；仓库整体仍是历史遗留的 84 个错误，本轮**没有新增**。
- 实测：52 字整段 → 2 条（29+22）；85 字技术回答 → 3 条，`500N`/`2000N`/`1612N` 都没被劈开；模型写了空行的照旧按空行分。
- bot 已重启（`00:42:05 Bot 1905857358 connected`）。

**复盘启示**

- **prompt 管"说什么"，代码管"怎么落到屏幕上"**。分条、停顿、标点这三件事写进 prompt 只会变成"第三个要表演的任务"，写在代码里才是免费的、稳定的。

- **加延迟之前必须先加锁**。UI 层的观感改动往往会把原本被速度掩盖的并发问题暴露出来。
- **可关闭的开关比"正确的默认值"更重要**。线上出问题时，能一句话关掉比能一句话改对有用。

**主题**：档 A（分条 + 停顿 + 句号剥离 + 会话锁）上线后，重新数一遍九个维度，明确"下一步该动哪一层"。记分牌已同步进 `docs/活人感调研.md` 第三节。

**现状**

- ✅ ③ 说几条、④ 每条多长：已从 prompt 建议变成代码硬约束。
- 🟡 ⑤ 不完美：只做了"句末不加句号"和"逗号→空格"；错字、碎片、大小写没有。
- 🟡 ⑦ 记忆：长期 md、群文化、`save_glossary` 有；好感度、自动黑话挖掘没有。

- **⑤ 的错字必须排在 ① ② 之后。** 我们花了七版 `uncertainty.md` 才守住"不让假事实、不编经历"，此时注入错字是在自己刚修好的信任面上再开一个口子。**不完美要建立在"能判断场合"之上，否则就是纯减分。**
- **⑥ 的价值是替 prompt 减负。** 心情/动作/记忆摘要一旦跨轮保存，`uncertainty.md` 里一半的"你别是怎样的"可以改成"你现在是什么状态"，硬线数量能实打实降下来。

**顺手发现的机器人腔**：`qq_bot/chat/turn.py:73`、`qq_bot/ai/openai_client.py:134`、`qq_bot/agents/base.py:71` 三处兜底话术都是 `"AI暂时无法响应，请稍后重试"`。它同时违反 `constraints.md` 的"不主动 AI 自述"—— 一句"嗯…卡住了 等下"就够了。这类固定句式是观感上最便宜的修复。

**复盘启示**

- **维度之间是有依赖的，不能按"哪个便宜先做哪个"排。** 便宜但方向错的改动（错字、乐子、更多硬线）会抵消已经做对的部分。
- **每补一个维度，先问"它替掉了 prompt 里的哪几条"**。替不掉就别做 —— 那只是在同一层继续堆。

## 2026-10-24 · 不 @ 也触发：入口已经在了，卡的是「用哪种通道发」

**主题**：用户问"能不能不 @ 自动触发"。查完代码的结论是：**收消息的前置条件已经具备，真正的约束在发送侧**。这条约束决定了自动触发的形态。

**代码事实**

- 全量群消息**已经在收**：`.env:16 QQ_GROUP_FULL_MESSAGES=true` → `qq_bot/plugins/qqbot_official/__init__.py:167-175` 的 `full_matcher`（priority 7、`block=False`）把非 @ 群消息写进成员的 thread，并 `schedule_compress(gid)`。只是它**只落库、不触发 AI**。
- 触发判定只有一处：`is_group_trigger`（`qq_bot/platform/qqbot/incoming.py:46`）—— `GROUP_AT_MESSAGE_CREATE` 直接过，`GROUP_MESSAGE_CREATE` 要求 `mentions_me`。
- 平台能力已经抽象出来了：`QQ_CAPS.can_see_all_group_messages = _FULL_GROUP`（`incoming.py:22-27`），所以上层不用关心是不是全量模式。
- **发送侧的分叉**：`QQReply._send_once`（`qq_bot/platform/qqbot/reply.py:63-89`）里，`passive=True` 走 `bot.send(event, seg)`（带 msg_id，不花额度），`passive=False` 走 `bot.send_to_group(group_openid=..., message=seg)`（**主动消息，受平台额度限制**）。现有兜底是"主动消息失败 → 退回被动回复"，但那条兜底假设手上有原事件；**对一条没 @ 过 bot 的消息，这个假设不成立**。
- 现网证据：日志里 10-19、10-20 各有一次 `QQ 主动消息发送失败，回退被动回复`，说明主动消息通道是通的但会偶发额度/权限失败。

**判断**

1. 自动触发的第一版**不该**从"主动消息"开始。无 @ = 没有 msg_id = 只能主动推送，而主动消息额度是最稀缺的资源，一旦用光，机器人就变成"不该说话时说话了，该说话时说不出来"。
2. 有一条**不花额度**的捷径：QQ 的被动回复窗口是"5 分钟内 / 最多 5 次"。所以在**最近有人 @ 过 bot 的 5 分钟内**，对群里其他消息接话可以复用那个窗口 —— 观感上就是"刚聊完顺嘴接一句"，恰好也是最像真人的时机。
3. 因此自动触发按成本分三层：**L1 窗口内接话**（0 额度，先做）→ **L2 每日少量主动**（花额度，需预算与白名单）→ **L3 全天候激活**（要申请额度 + 激活度打分，是档 C）。
4. 有一个平台未知数必须实测：**非 @ 的群消息能否用它的 msg_id 走被动回复**。这决定了 L2 的形态（是"每天 N 条主动"还是"根本发不出去"）。

**复盘启示**

- **"能不能收到"和"能不能发出"是两个完全不同的问题**，前者是权限，后者是额度。ChatBot 的拟人化设计里，额度往往是隐藏的硬约束 —— 它决定了你能做"少而准"还是"多而糙"。
- **命中既有窗口 > 创造新通道**。真人在群里接话，也总是顺着刚才的对话，不会凭空插进一个没人理他的话题。

## 2026-10-24 《设计：短句能力与「戳一戳」——一个缺预算，一个缺动作》

完整方案见 `docs/短回复提醒设计.md`（209 行，含接口、档位表、风险清单、验收标准）。这里记原理与取舍。

### 1. 为什么现在说不了短句

不是模型不会说，是**代码里没有任何预算**：

- `ModelProfile.max_tokens` 默认 **16384**（`qq_bot/ai/model_registry.py:39`），`qq_bot/chat/turn.py:294` 原样透传 → 物理上不设限。
- `prompts/chat/style.md:6` 写了「1–10 字」，但那只是建议，被前后几千 token 的规则稀释，且没有反例成本。
- `split_for_reply`（`qq_bot/platform/reply.py:40`）只把长文**切成 ≤4 条 × ≤30 字**——切的是"一条长消息"，不是"让它一开始就短"。
- `qq_bot/tools/send_sticker.py:19`「表情包不能替代回答」+ `turn.py:344` 空回答兜底 `"AI暂时无法响应"` → **0 文本档被自己禁掉了**。

教训：**"说得短"是预算问题，不是措辞问题**。在 prompt 里加十遍"要短"都不如一个 `max_tokens` 和一个字数上限。这是 v1→v7 改十四版 prompt 却始终"AI 感重"的同一根因——我们一直在改"说什么"，没改"说多少"。

### 2. 话量预算的三个设计判断

1. **抽签而不是自适应**：同一个人被问同一句话，有时"嗯"有时说三句；这种**方差**本身就是人味。全自适应会变成"永远恰好得体"，那是表演。分布 55% 极短 / 35% 正常 / 10% 详细。
2. **修正规则兜底**：含数字/型号/疑问词/长消息时抬到 normal 以上，避免"技术问题被一个字打发"。
3. **预算提示句放在 system prompt 最末位**：① 近因偏好对格式约束最有效；② 前缀不变，**prompt 缓存仍命中**（缓存按前缀匹配）。

### 3. 一个容易踩的坑：`max_tokens` 不是纯"回答长度"

推理 token 和**工具调用 JSON** 都吃这个额度。预算设成 40，模型可能还没发出 `send_sticker` 的参数就被截断，回答直接空。所以物理上限必须 `max(512, budget.max_tokens)`，并观测 `finish_reason=length` 的占比（>5% 说明下限不够）。**把预算当"回答长度"直接塞进 `max_tokens` 是最容易翻车的一步。**

### 4. 为什么"戳一戳"做不了

实测 `nonebot/adapters/qq/bot.py` 全量端点：

| 能力 | 群聊通道 | 依据 |
|---|---|---|
| poke | ❌ | 全文件无 poke 端点 |
| 贴表情 | ❌ | `put_message_reaction` 等三个方法都是频道 `/channels/{id}/messages/{id}/reactions` |
| 撤回 | ✅ | `delete_group_message`（`bot.py:2323`） |
| 按钮消息 | ⚠️ 有接口 | `post_group_messages(msg_type=2, markdown+keyboard)`；回调 `INTERACTION_CREATE` + `put_interaction`（`bot.py:1853`），但**群机器人需要权限申请**，且语义是"请对方戳我"，反了 |
| 引用回复 | ✅ 天然 | 被动回复带 `msg_id` 即渲染成"回复某条" |

所以 poke 是**通道缺动作**，不是代码缺实现。三条路：换 NapCat 通道（真但等于重写平台层）/ 按钮彩蛋（权限门槛 + 语义反）/ **语义等价「轻招呼」**（引用 + 一个字、只发「戳戳」表情包）。

### 5. 关键取舍：把"戳一戳"重定义为「轻招呼 nudge」

不要试图模仿 poke 的动画，而是给"碰一下"这个**意图**找最便宜的表达：引用你那条只回一个"？"，或只发一个 `戳戳`（表情库 `stickers.yaml:31-34` 已有 `tiaodou.gif`，不用新素材）。触发做窄（≤6 字的叫名/喂/在吗），每会话 10 分钟一次。

**教训：平台没有的能力，先在"意图层"找等价物，再去想换通道。** 换通道是战略决策，等价物是当天的活。

### 6. 复盘：为什么这两件事能先于 ① 做

它们只改"说多短 / 用哪种轻动作"，不碰触发判断、不碰事实硬线（`uncertainty.md` 上一轮刚守住的"不让假事实/不编经历"）。所以可以独立上线、独立回滚（两个开关），不会重演 v1→v7 那种"改措辞改到自我矛盾"的循环。

**顺带记一条：AI 感的两个来源是"每一句都必须回答"和"每一句都必须完整"。前者要 ①，后者是这两个动作能解决的。**
## 2026-10-24 · 自动接话 L1：蹭被动窗口，记账取最保守口径

**主题**：让机器人「没被 @ 也能顺嘴接一句」。第一版只做 L1 —— 复用最近一次 @ 留下的被动回复窗口，零额度成本。

**问题定义**

群里没人 @ 时，机器人即使看见了消息也无动于衷，读起来就是「一个等着被点名的工具」。想让它在话题正好接得上时插一句，但**发出消息的通道**受平台约束：QQ 官方机器人对「没有 msg_id 的消息」只能发主动消息，而主动消息有每日额度，用光了连该说的话都说不出来。

**根因**

不是「收不到消息」：`.env:16` 的 `QQ_GROUP_FULL_MESSAGES=true` 让 `full_matcher`（priority 7、`block=False`）早就在收全部非 @ 群消息，它只是写库不触发 AI。真正的瓶颈在发送侧 —— `QQReply` 的被动/主动分叉决定了「有没有 msg_id」等价于「花不花额度」。

**方案**

1. `qq_bot/chat/passive_window.py`：内存 TTL 登记表。`_dispatch` 每次 @ 触发时 `register(group_key, reply)`，条目 300 秒过期、上限 512 个群；`acquire()` 只在窗口未过期且 `used < 4` 时返回 reply。
2. `qq_bot/chat/activation.py`：纯函数打分。引用别人 +3、出现 bot 名字 +3、与 bot 上句有实词重叠 +2、问句 +1、出现「你/你们/咱」+1、bot 十分钟没说话 +1；`score >= min_score(4)` 且 `rng() < probability(0.6)` 才放行。命令、空文本、同一人 60 秒内连发 ≥3、冷却中、日额度用尽、无窗口，一条命中就否决。
3. `qq_bot/chat/autotrigger.py`：编排层。维护每群状态（90s 冷却、每日 6 条、跨天按 `date.today()` 清零、发送者 streak 表上限 200），把信号凑齐交给 `decide`，通过后把 reply 换成 `WindowReply` 再跑 `run_turn`。
4. `WindowReply` 适配器：`max_parts = 1`（自动接话只说一条）、`mention()` 降级成 `passive()`（顺嘴接话不 @ 人）、`image()` 丢弃（不发表情包）、`uses_proactive = False`。
5. 插件钩子：`handle_full_message` 里构造一次 `Incoming`，先 `_record_full_message(bot, event, incoming=incoming)` 落库，再 `maybe_autotrigger(..., incoming=incoming)` —— 同一条消息只构造一次，不重复下载媒体。
6. 埋点：无论放不放行都打一行 `autotrigger group=... allowed=... score=... reason=... sender=... streak=... daily=.../... text=...`，第一周靠它调阈值。

**取舍**

- **为什么先做 L1 不做主动消息**：L1 的成本是 0 额度，错了最多「多说一句」；L2 花的是每日额度，错了会挤掉真正该说的话。先用最便宜的通道验证「判断层准不准」，再谈花钱。
- **为什么自动接话只说一条**：窗口里最多剩 1 次回复名额（见下条），而且真人插话本来就是一句；拆成 4 段既超发又像刷屏。
- **记账为什么取保守口径**：一次 @ 回复最多用 4 段，真实剩余名额可能是 1 也可能是 0（取决于模型那轮说了几段），而**平台不告诉我们剩几次**。登记时直接把 `used` 记到上限 4，窗口只允许 1 次自动接话。宁可少接一句，也不能超发被平台拒 —— 被拒的观感是「机器人坏了」，少说的观感只是「它没插话」。
- **为什么名字/问句这些信号只做加法不做乘法**：加法可解释、可单测、调阈值时能看出「是哪条把它抬过线的」；乘法在日志里只剩一个数，调不动。
- **为什么状态全放内存**：这是「锦上添花」的功能，进程重启清零完全可接受；落库反而引入一致性问题（多进程、热重载）。

**复盘启示**

- **先分清「收得到」和「发得出」**。前者是权限，后者是额度；拟人化设计里，额度常常是隐藏的硬约束，它决定你做「少而准」还是「多而糙」。
- **当一个资源（回复名额）不可观测时，唯一安全的记账方式是取最坏情况**。乐观记账在演示里永远看不出问题，上线后才会以「偶发发送失败」的形式还债。
- **埋点先行**：判断层的第一版一定是拍脑袋的阈值，`score/reason` 那行日志比任何设计文档都更能告诉你「它什么时候会乱说话」。
- **L2 能否落地取决于逐群的 `allow_proactive_msg`**（`bot.get_group_bot_state()` 的返回字段）。上线前先跑一轮探测收集结果，别拿「我们以为有额度」当前提。

## 2026-10-24 Bug：判定用错了文本 —— hint 里的那个「你」让每条消息白得一分

**问题定义**

L1 自动接话上线后，用户在群里发了一句「人呢」，日志是：

```
autotrigger state group=C69128... recv=all allow_proactive=True role=member
autotrigger group=C69128... allowed=False score=2 reason=veto:no_window ... text='人呢'
```

`veto:no_window` 是对的（那会儿没 @ 过它，没有被动窗口）。可疑的是 **`score=2`**：「人呢」能拿的分只有疑问句「呢」这一项，值 1 分。多出来的 1 分从哪来？如果每条消息都白送 1 分，那么 `min_score=4` 实际是 3 —— 一整个阈值被悄悄拉低了 25%，而且日志上看不出来。

**根因剖析**

`qq_bot/chat/autotrigger.py` 里有两种文本，故意分开的：

- `text`：用户原话，用来**判断**；
- `turn_text = _text_for_turn(incoming, config)`：**给模型看**的文本，前面拼了一句提示 `（这没人在叫你，你只是顺嘴插一句）`，让模型分清「顺嘴接」和「被 @」。

问题出在判定时用错了那个变量：`turn_text` 被拿去算了 `second_person`、`mentions_bot_name`、`is_question`。而那句 hint 里恰好有「你」——

```python
second_person = any(word in turn_text for word in activation.SECOND_PERSON_WORDS)  # 「你」命中 hint
```

于是**每一条消息都白得 `WEIGHT_SECOND_PERSON` 那 1 分**，「人呢」= 疑问句 1 + hint 里的「你」1 = 2，与日志完全对上。

同一个根因还有第二个症状，更隐蔽：`decide()` 的第一个参数也被传成了 `turn_text`，而 `_veto_reason` 靠 `if not stripped: return "media_only"` 拦纯图片消息。hint 让 `stripped` 永远非空，**纯图消息的 `media_only` 否决彻底失效** —— 它会带着 0 分继续往下走。之前 `test_media_only_and_blank_skipped` 之所以是绿的，是因为它恰好靠「0 分 < min_score 4」被拦下，属于**测试通过、逻辑错误**：把 `min_score` 调到 0，一张图就能触发一次自动接话。

**解决方案**

判定一律只吃用户原话，hint 只进模型那一侧：

```python
turn_text = _text_for_turn(incoming, config)   # 只给 _run_auto_turn 用
second_person = any(word in text for word in activation.SECOND_PERSON_WORDS)
decision = activation.decide(
    text,
    is_command=text.startswith("/"),
    mentions_bot_name=any(name in text for name in _names(config)),
    is_question=activation.looks_like_question(text),
    ...
)
```

补两条回归测试（`tests/test_autotrigger.py`），都用「旧实现会触发、新实现不触发」的方式钉死：

- `test_hint_text_does_not_add_score`：hint 含「你」、消息是「今天 35 度」、`min_score=1`、概率 1.0 → 必须不接；
- `test_media_only_is_vetoed_even_with_hint`：空文本 + 一张图、`min_score=0`、概率 1.0 → 必须被 `media_only` 拦下。

全量 `pytest` 196 → **198 passed**，改动文件 ruff 通过（仓库 84 个历史错误不动），重启后 `Bot 1905857358 connected`。

**复盘启示**

- **「给模型看的文本」和「用来判断的文本」必须分离，而且要在类型上就分开**。这里两个都是 `str`，编译器帮不了你；只要它们在同一个函数里同时存在，就一定会有人（包括我）拿错。教训是：给模型看的文本不要提前拼进主流程变量，最好在真正调模型的那一步才拼。
- **提示词会反噬判定逻辑**。任何一句写给模型的提示，都会成为程序字符串的一部分；hint 里写「你只是顺嘴插一句」，等于给打分器塞了一个第二人称。写提示词时要想一句：「这句话会不会被别处的代码读到？」
- **测试绿了不代表逻辑对**。`test_media_only_and_blank_skipped` 一直绿着，因为它被另一个条件顺路拦住了。对于「否决顺序」这类逻辑，测试要断言**具体理由**（或把其他阈值调到不生效），而不是只看「没发出去」。
- **线上日志里的数字要能对上账**。这次是「score=2 但只能解释 1 分」这点不对劲暴露了整个问题。凡是日志里有分数、耗时、计数的地方，第一次就该手算一遍；算不平的地方就是 bug 藏身处。

## 2026-10-25 · GBF wiki 角色索引：先落 CSV，别急着做查询

给 bot 加「查碧蓝幻想角色/武器」能力的第一步，是把检索索引拿到本地。调研结论与实现：

**接口**：`https://gbf.huijiwiki.com/index.php?title=Data:角色列表.tabx&action=raw` 一次返回整张表（400KB JSON，1021 行 × 45 字段），不需要登录。Data 命名空间（ns 3500）下还有 `武器列表`、`召唤石列表`、`物品列表`、`译名对照表` 等 30 个同构数据集，武器库 2979 行。

**坑一：Cloudflare 指纹**。直接 `httpx` / `curl`（哪怕完整 Chrome 请求头、走代理或直连）一律 403 交互式挑战，判定依据是 TLS/HTTP2 指纹而非出口 IP。必须用 `curl_cffi` 的 `Session(impersonate="chrome")`；且 TLS 会被随机掐断（`SSL_ERROR_SYSCALL`），必须重试 3 次。为此新增依赖 `curl_cffi>=0.16.3`（`uv add`）。图片 CDN `huijistatic.com` 反而无防护，普通 HTTP 可下。

**坑二：页面里的面板数值是空的**。`action=parse` 返回的 HTML 里 HP/攻击力是 `<div class="js-value" data-vkey="mhp">` 占位，由前端 JS 回填 —— 数值只能从 tabx 取，别去解析页面数值。

**脚本**：`scripts/fetch_gbf_char_index.py` → `data/gbf/characters.csv`（1021 行 / 48 列，433KB，utf-8-sig 便于 Excel 直接打开）。
- 在 45 个原始字段后追加了三列：`aliases`（`nickname` + `search_nickname` 按 `;` 拆开、去重、用 `|` 连接，如「飞机头|🚲|🛵|✈头」）、`search_text`（中文名/日文名/英文名/头衔/声优/别名小写拼接，供子串匹配）、`page`（`Char/{id}`，详情页直接可用）。
- 清洗：出现过的两类脏值都是「序列化痕迹」而非语义 —— 日期统一带 `##` 前缀（**不是**「未实装」标记，2014 年的老角色也有，别被自己脑补的语义骗了，第一版写成 `(预定)` 是错的），wikitext 链接 `[[Premium Draw]]` 需剥成纯文本。
- `data[0]` 在 `武器列表.tabx` 里是类型行（id 单元格为「字符串」），角色表没有；脚本按「id 能否转 int」过滤，两种都兼容。

**频率**：全程只打了 3 次请求（表本身 1 次 + 校验 2 次），按灰机人机协议控制在「微微量」，后续实现也要沿用这个量级。

**未完**：灰机《人机协议》要求批量/自动获取需书面授权，且「机器人账号获取的内容只可用于灰机站点建设」。已拟好问询信准备发 `support@huiji.wiki`，**拿到答复前不做详情页批量抓取、不发图**，只保留这份本地索引。

## 2026-10-25 · GBF 角色详情：5 个样本先算清楚「一条查询到底多少钱」

拿 5 个 SSR（火/水/土/风/光 各一，`3040006000/3040007000/3040002000/3040003000/3040004000`）各打 1 次 `action=parse`，把奥义/技能/被动抽成结构化 JSON，顺便把「一条查询的代价」量化：

| 口径 | 单角色 | 5 个合计 | 全量 1021 个推算 |
|---|---|---|---|
| 线上传输（brotli 压缩后 body） | 10.1–13.4 KB，均值 **12.1 KB** | 60.7 KB | ≈ 12 MB |
| 解压后 JSON（API 原始响应） | 87–102 KB，均值 **92.7 KB** | 463.7 KB | ≈ 92 MB |
| 抽干后落盘（我们的 JSON） | 15.3–20.4 KB，均值 **17.4 KB** | 87.1 KB | ≈ 17 MB |

压缩比 7.63x —— 也就是说「按请求次数限流」和「按流量限流」差了一个数量级，跟站长沟通时该说清楚是按哪个口径。

**解析坑（都是踩出来的）**：
- lxml 下 `span/@id` 会返回 `.E5.A5.A5.E4.B9.89` 这种转义形式（同一个 span 还能取到两个 id 值），改拿 `span.mw-headline` 的**文本**当章节标题才稳。
- `span.name_chs` 里嵌着 `.tooltips-content` 装日文名，用 `text_content()` 会把中日文名粘在一起（「一对一的“瞬间”タイマンの"瞬間"」），必须取 span 自身的 `.text`。
- 使用间隔的数值不在 `label-item` 自己的 tail 上，而在外层 `inline-block` 包裹的 tail 上，要往上找一层。
- 状态图标给的是 22px 缩略图 URL，渲染要 64px 原图：`.../uploads/thumb/<path>/22px-x.png` → `.../uploads/<path>`，注意 path 里已含文件名，别再拼一次。
- 纯文本化会压平表格类描述（如「种族数 1/2/3+ → 攻击力 10%/20%/30%」），这是 `text_content` 的固有限制；已把原始 HTML 一起存了，后续要补表结构不用再发请求。

**顺带的结构判断**：描述里内联的状态图标必须保序（22px 图标夹在「防御力」和「+10%」之间），所以 JSON 里除了 `desc` 纯文本，还并存 `segments`（text/br/status 三类片段）和 `statuses` 汇总 —— 渲染成图时按 segments 画，别按 desc 猜位置。三份字段有冗余，落盘体积因此翻倍（10.8 → 17.4 KB/角色），这是刻意的。

**脚本**：`scripts/fetch_gbf_char_detail.py`（`--ids` / `--count` / `--keep-html` / `--from-html` 离线重解析），产物 `data/gbf/details/{id}.json` + `_summary.json` + `{id}.html`。本次总请求量：5 次抓取 + 1 次探测 `download_size` 可用性 = 6 次，仍在「微微量」范围。

## 2026-10-25 · 立绘有多大：一张图顶两条详情

拿莉莉（`3040007000`）量了 `Profile_3040007000_01|02|03.png`（01 初始 / 02 一突 / 03 终突；该角色没有 `_81` 额外形态，404）：

| 形态 | 尺寸 | 文件 | 格式 |
|---|---|---|---|
| 01 初始 | 2239×1920 | 390.2 KB | 实际是 **WebP**（URL 却以 `.png` 结尾） |
| 02 一突 | 2250×1723 | 646.1 KB | WebP |
| 03 终突 | 2189×1649 | 730.5 KB | WebP |
| 合计 | — | **1.75 MB** | — |

三个反直觉的点：

1. **URL 是 `.png`，内容是 WebP**。huijistatic 按 `Accept` 协商：Chrome 头拿到 WebP，`Accept: image/png` 拿到真 PNG 但**体积翻倍到 1054.6 KB**。Pillow 读 WebP 没问题，但下游任何按扩展名判断格式的代码都会错（QQ 的 `file_image` 走魔数检测，暂不受影响）。
2. **一张立绘 ≈ 两条半详情查询**（390 KB vs 12.1 KB 线上）。缓存策略要按图片单独算，别和数据请求混在一起。
3. **构图是横的**：2239×1920 近方形、2250×1723 扁，不是常见竖版立绘。按 3:4 竖卡裁会切掉两侧，做卡片前得先看清画面主体在哪。

**真的要用原图吗**：CDN 的 thumb 服务按宽度缩放，同样一张 01：

| 宽度 | 体积 | 压缩比 |
|---|---|---|
| 800px | 106.8 KB | 0.27x |
| 1200px | 186.2 KB | 0.48x |
| 1600px | 274.3 KB | 0.70x |
| 原图 2239px | 390.2 KB | 1.00x |

渲染卡片用 800–1200px 足够，能省 55–73% 流量。缩略图 URL 复用 mediawiki 分桶：`https://huiji-thumb.huijistatic.com/gbf/uploads/thumb/{h[0]}/{h[:2]}/{文件名}/{宽度}px-{文件名}`。

**脚本**：`scripts/fetch_gbf_portrait.py`（`--ids` / `--variants` / `--thumb` / `--no-save`），产物 `data/gbf/portraits/`，走 CDN 不碰 wiki API。本轮立绘测试约 18 次静态资源请求（含复跑与宽度对比），无一次 API 请求。
