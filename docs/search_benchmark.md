# 搜索双链路基准：legacy vs improved

- 分支：`feat/search-pipeline-benchmark`（基线 `5c043e8`）
- 日期：2026-10-21（Asia/Shanghai）
- 模型：`deepseek-v4-flash`；搜索源：Tavily
- 原始数据：`docs/search_benchmark_raw.json`
- 6 题合计：legacy **182.04s / 179,435 tokens**，improved **79.30s / 34,365 tokens**

## 结论摘要

- **速度**：improved 总耗时 79.30s，legacy 182.04s，约快 **2.30×**；单题平均 30.34s → 13.22s。
- **成本**：improved 总 token 34,365，legacy 179,435，约省 **80.8%**；主要来自不再让子 Agent 做多轮工具推理，以及把“检索”和“组织回答”拆成一次轻量规划 + 一次回答。
- **质量**：6 题里 improved 有 4 题可直接用（S 赛、新番、天气、油价），2 题暴露边界（赛马娘下月大赛两链路都没数据；日服活动 improved 覆盖较少）。legacy 在需要多源拼图的题上更全面，但慢且贵。
- **结论**：日常时效问题默认 `standard` 已够用；复杂对比/多约束问题再走 `deep`。赛马娘这类垂类环境题，靠通用网页搜索本身就不稳，应接官方/社区结构化数据源。

## 实验设置

- **legacy**：保留原有的 `SearchAgent`（`max_rounds=3`）+ `batch_search` + `web_fetch`，检索报告再交给同一个最终回答提示词。
- **improved**：`SearchPipeline`，一次轻量 query 规划 → 并行 Tavily 搜索 → 清洗/去重/重排 → 按模式抓 0/2/3 篇正文 → 生成 `[S1]…[Sn]` 证据 → 同一个最终回答提示词。
- 两链路使用**同一个模型、同一个最终回答 prompt、同一批问题**；improved 每题 `force_refresh=True`，不吃上一次运行的缓存。
- `总耗时` 含检索与最终回答；`检索` 只含检索阶段。token 为整题所有 LLM 调用的总和。
- legacy 的“来源”是报告里出现的 URL 数，不等于实际抓取页数；improved 的来源是最终选中的证据数，两者只作粗略参考。

## 改动清单

- 新增 `qq_bot/search/` 纯服务层：`types.py`（`SearchItem`/`SearchOutcome`）、`cache.py`（LRU+TTL，只缓存 Tavily 原始结果）、`planner.py`（query 规划、时间范围推断）、`rerank.py`（清洗、URL/标题去重、词项覆盖 + 日期 + 域名多样性）、`pipeline.py`（quick/standard/deep 编排、reader 降级、`[S#]` 上下文）。
- 新增 `qq_bot/tools/search_tool.py`，注册主模型工具 `search`；`qq_bot/chat/turn.py` 把主模型可见工具从 `search_agent` 换成 `search`，仍限制每轮最多搜索一次。旧 `search_agent`/`SearchAgent` 保留给 legacy 基准和兼容。
- `qq_bot/tools/tavily_client.py`：`TavilyClient` 支持注入 `AiChatConfig`（基准/测试可脱离 NoneBot），把大量 `print` 改为 logger，保留 432/433 多 key 轮换。
- 新增 `prompts/agents/search_answer.md`：只依据 `[S#]` 证据、标注截至日期、证据不足直说、200 字以内；`{{ current_date }}` 由调用方注入。
- 新增 `scripts/search_benchmark.py`：双链路跑同一批问题，记录答案、耗时、token、来源、错误，增量写 raw JSON。
- 新增 `tests/test_search_pipeline.py`：模式路由、清洗、域名多样性、编号、quick/standard 的 reader 行为、缓存、日期解析与按新到旧排序。
- 时效修复：`time_range` 非空时对证据做 `sort_by_recency`，并把当天日期注入最终回答 prompt，避免“10-21 还在引用 10-15 的旧调价窗口”。

## 调试记录

- 第一次跑 improved 时，planner 的 JSON 被截断，产生损坏 query，最终答案为空；已让解析器兼容截断/双重编码数组，并把规划调用 `max_tokens` 收紧到 600。
- 修复前第二次跑：improved 合计 87.33s / 34,302 tokens，legacy 201.93s / 213,324 tokens；速度和成本优势明显，但油价题引用了 10-15 的旧窗口。
- 根因不是搜索没拿到新结果，而是证据按相关性排在前、旧文章先进入上下文，回答模型又没有被明确告知“今天几号”。修复后本轮油价题正确给出 10-29，且两链路一致。

## 局限与下一步

- 单模型、单搜索源、每题单次运行，结果会受 Tavily 索引和模型采样影响；这不是统计显著性实验。
- legacy 的 `source_count` 是 URL 计数，和 improved 的选中证据数不可直接比较。
- 赛马娘下月大赛两链路都没拿到可靠数据，说明通用搜索对垂类版本环境不够；下一步应接官方公告/游戏 API/社区数据库，而不是继续堆 query。
- improved 的 200 字上限适合 QQ 聊天，但会牺牲细节；需要长答时可让回答层按 `deep` 放宽。
- 下一步：按 intent 路由（时效/教程/垂类/对比）、加权威域名白名单、对官方页面做结构化解析、补缓存命中率和 p95 延迟指标。
